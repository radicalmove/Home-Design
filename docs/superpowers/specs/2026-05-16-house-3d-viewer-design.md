# House 3D Viewer Design

## Purpose

Create a first navigable 3D version of the current house so the existing measured/photo model can be explored with keyboard and mouse.

The goal is not a final photorealistic architectural render. The goal is a believable current-state walkthrough that uses the 2D plan as geometric authority, uses photos to guide visual treatment, and leaves room for later proposed-layout previews with AI-generated filler materials.

## Context

The project already has:

- `DATA/house_model.json` as the source of truth for rooms, current structure, site context, openings, photo evidence, and confidence levels.
- Python renderers in `CODE/home_design/` that generate static or interactive HTML/SVG outputs.
- `OUTPUT/jpeg_photos/` as a compact set of converted photo evidence.
- A reference-style 2D plan generated by `CODE/home_design/reference_plan.py` and wrapped by `CODE/home_design/reference_plan_viewer.py`.
- Existing regression tests under `tests/`.

The 3D viewer should extend this model-driven workflow rather than introduce a separate hand-built web app.

## User-Approved Scope

The first milestone should show the current house only.

It should include:

- A generated `OUTPUT/house_3d.html` page.
- Keyboard and mouse exploration of a 3D scene.
- Main house room geometry, walls, openings, floors, deck, driveway, garage/shed, cottage, and basic property context.
- Photo-inspired materials and generated/procedural filler textures for visual cues.
- Clear treatment of measured/photo-verified versus inferred content.

It should not include a proposed-layout toggle yet. The current house baseline should become the reference target for later scenario views.

## Recommended Approach

Add a Python-rendered Three.js viewer:

- New module: `CODE/home_design/three_d_viewer.py`.
- New CLI command: `python3 -m CODE.home_design.cli house-3d --output OUTPUT/house_3d.html`.
- New regression tests focused on generated HTML and embedded scene data.

This fits the existing repository because the model remains the authority and generated HTML remains an output artifact, like the current 2D viewers.

## Geometry Model

Use metres as scene units.

Coordinate mapping:

- Model `x` maps to Three.js `X`.
- Model `y` maps to Three.js `Z`.
- Height maps to Three.js `Y`.
- Room/floor heights come from `dimensions_m.height` where available, with sensible defaults from existing model assumptions.

Geometry should be built from current model data in this order:

1. Room layouts from `rooms[*].layout` for floor slabs and simple room volumes.
2. Current structure spaces from `current_structure.spaces` where they contain more accurate display geometry.
3. Current structure features from `current_structure.features` for photo-verified openings.
4. Existing reference-plan wall/opening definitions where they are currently the most accurate source for wall breaks.

The first implementation can approximate wall solids and opening cutouts. It should avoid pretending to have exact millimetre-accurate 3D joinery where only 2D/photo evidence exists.

## Scene Content

The first scene should include:

- Floors for all main spaces: kitchen/dining, lounge, sunroom, hallway, master bedroom, office, bathroom, bedroom 2, entrance, laundry, and toilet.
- Exterior and interior wall solids with practical default heights.
- Windows, sliders, and door openings represented visibly enough for walkthrough orientation.
- Sunroom glazing as a prominent transparent/light-framed element.
- Deck, driveway/path, lawn/property boundary, garage/shed, and cottage as simplified context volumes.
- Basic furniture or scale cues only where already present in the reference plan or useful for orientation.

Interior ceilings can be omitted or toggleable in the first pass so navigation is easier.

## Visual Treatment

Use photo-inspired and generated/procedural filler materials:

- Timber or warm neutral floors for living/bedroom areas.
- Tile-like surfaces for bathroom, laundry, and toilet.
- Painted plasterboard wall materials.
- Transparent or lightly tinted glazing for windows and sunroom.
- Timber deck boards.
- Concrete/paver driveway and paths.
- Lawn/planting color for site context.

AI-generated filler assets should be treated as replaceable local assets, not as geometry authority. The scene should work with procedural CSS/canvas/Three.js materials first, then allow texture files to be swapped in later.

When future layout scenarios are added, the same material system should make changed rooms look plausible even when no direct photo exists for the proposed state.

## Interaction

The generated HTML should provide:

- Pointer-lock first-person mouse look.
- `W`, `A`, `S`, `D` movement.
- Optional `Q`/`E` or arrow-key vertical/side movement if useful.
- A reset-view control.
- A small overlay showing the current room or selected context where feasible.
- A fallback message if WebGL or the Three.js dependency fails.

The starting camera should be positioned so the user can immediately understand the house context, with a quick path into the main living/kitchen area.

## Data Flow

The renderer should embed a compact scene config in the HTML:

- Units and orientation metadata.
- Room polygons/rectangles.
- Current structure spaces and features needed for openings.
- Site/context elements.
- Material assignments by room category and feature type.
- Photo evidence links for rooms/features where available.
- Confidence labels.

Browser JavaScript should:

1. Read the embedded config.
2. Create the Three.js scene, camera, renderer, lights, and controls.
3. Build floors, walls, openings, site context, and material treatments from config.
4. Attach keyboard/mouse interactions.
5. Keep room/feature metadata available for overlays and later scenario comparison.

## Error Handling

If a room layout is missing or malformed, skip that room and expose a warning in the embedded debug/status panel.

If Three.js cannot load, show a plain HTML error panel rather than a blank page.

If WebGL is unavailable, show a clear unsupported-browser message.

If photo evidence is missing, fall back to room-category material presets.

## Testing

Use focused regression tests before implementation:

- `render_house_3d_html(model)` returns a full HTML document.
- The HTML includes a Three.js scene bootstrap, pointer-lock controls, and keyboard input handlers.
- The embedded config includes representative room IDs such as `kitchen_dining`, `lounge`, `sunroom`, `bedroom_2`, `laundry`, and `toilet`.
- The embedded config includes representative feature/opening IDs such as `deck_door_group`, `sunroom_lounge_slider`, `entrance_deck_slider`, and `sunroom_wraparound_glazing`.
- The HTML includes material categories for timber, tile/wet area, painted wall, glazing, deck, pavers/concrete, and lawn.
- The CLI supports `house-3d` and writes the requested output path.

After implementation, run the full unit suite and visually verify the generated page by serving the repository locally.

## Non-Goals

- No proposed-layout toggle in the first milestone.
- No exact structural engineering claims.
- No physically exact lighting or shadow simulation.
- No full photogrammetry reconstruction.
- No automatic inference of hidden dimensions from photos.
- No dependency on AI-generated images for geometry correctness.
- No separate React/Vite application unless the generated HTML approach proves insufficient.

## Future Path

After the current-house 3D baseline is working:

1. Add proposed-layout model files or scenario overlays.
2. Add current/proposed switching in the same viewer.
3. Add AI-generated room/material filler textures for proposed spaces.
4. Add better opening cutouts and wall collision.
5. Add daylight/sun studies in 3D using the orientation data already in the model.
6. Add exportable screenshots or saved camera views for comparing design options.

## Approval Gate

Implementation should proceed as a tests-first change:

1. Add tests for the generated 3D HTML and CLI command.
2. Add the `three_d_viewer.py` renderer.
3. Add the `house-3d` CLI command.
4. Generate `OUTPUT/house_3d.html`.
5. Run tests and visually verify the page locally.
