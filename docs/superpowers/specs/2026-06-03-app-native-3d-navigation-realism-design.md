# App-Native 3D Navigation Realism Design

## Purpose

Replace the current packaged `house_3d.html` iframe with an app-native Svelte and Three.js 3D Navigation view that uses the current house model, saved furniture layout, site/photos evidence, and the known 30cm pile/floor elevation to create a much more accurate current-state walkthrough.

The goal is a credible, photo-informed digital twin of the current house, not a structural-engineering model or a full photogrammetry reconstruction. Accuracy should come first from the measured 2D/model data and saved furniture layout, then from photo-informed materials, lighting, and scale cues.

## Context

The current 3D Navigation mode is generated by `CODE/home_design/three_d_viewer.py`, then packaged as `apps/desktop-ui/public/views/house_3d.html`. It already contains useful model-driven geometry:

- room floors from `DATA/house_model.json`
- curated wall segments and opening gaps
- windows, doors, sliders, sunroom glazing, deck, driveway, garage/shed, cottage, lawn, fences/hedges
- simple procedural materials
- 7 hard-coded photo-cue fixtures

The main weaknesses are:

- it is an iframe/static generated HTML view rather than a live app view
- it does not consume the saved furniture layout from the Furniture Editor
- it has limited furniture geometry and only a few hard-coded fixture cues
- it does not model the house as raised on piles about 0.30m above ground
- it has simple lighting and no direct connection to the sunlight/time-of-year controls
- it lacks photo-viewpoint presets for visual comparison against project photos
- materials are procedural but still too flat and generic

The user has now asked for the 3D view to use all current project knowledge, including the base view, furniture, photos, and pile height, and to be iterated over 10-20 passes toward the most realistic practical result.

## Selected Approach

Use an app-native Three.js component rather than continuing to improve only the generated HTML iframe.

This means:

- Add a `ThreeDNavigationView.svelte` routed from `App.svelte` when `selectedView.mode === "three_d_navigation"`.
- Reuse existing Tauri commands for `load_design_review_data`, because that already returns the model and latest saved furniture layout.
- Build the 3D scene in TypeScript from a pure scene-config module so geometry can be tested without WebGL.
- Keep `CODE/home_design/three_d_viewer.py` as a development/reference renderer until the native view fully supersedes it.
- Preserve the existing manifest entry and 3D tab label so the user workflow does not change.

This is a larger change than a generated HTML tweak, but it is the right direction for a finished product because the view can refresh with saved furniture and later support design scenarios, animated transitions, sunlight comparison, and garden modelling.

## Architecture

### Data Source

The native 3D view should load:

- `DATA/house_model.json`, through `load_design_review_data`
- current saved furniture layout, through the existing app-data backed furniture layout loader
- catalog-derived object types where helpful for furniture height/material defaults
- photo evidence metadata from `house_model.photo_evidence.checks`

The actual saved furniture layout currently lives under:

`~/Library/Application Support/nz.home-design.desktop/projects/current-house/scenarios/current/furniture-layout.json`

The app should not hard-code this path in the frontend. It should use the existing Tauri command path.

### Modules

Add focused TypeScript modules under `apps/desktop-ui/src/lib/threeD/`:

- `sceneConfig.ts`
  - Converts model JSON and `FurnitureLayout` into a `ThreeDSceneConfig`.
  - Handles metre coordinate mapping, room geometry, wall segments, site elements, opening bounds, furniture objects, and pile/foundation data.

- `materials.ts`
  - Maps room/site/furniture types to material definitions.
  - Owns procedural texture generation inputs: carpet, vinyl plank, tile, deck timber, concrete, lawn, plaster, cabinetry, glass, dark sofa fabric, timber furniture.

- `furniture3d.ts`
  - Maps saved `FurnitureObject` types into recognisable 3D primitives.
  - Supports L-shaped couch, L-shaped desk, beds, cabinets, kitchen fixtures, bath, shower, toilet, vanity, wardrobe doors, partition walls, TV, fireplace, piano, dining table, stools, bookcases, desks, dressers, washer/dryer, sink, and fridge.

- `geometry.ts`
  - Shared geometry helpers: model display geometry to metres, polygon bounds, rotation transforms, wall segment extraction, pile/support placement, basic collision-free camera starts.

- `walls.ts`
  - Ports the curated wall network from `CODE/home_design/three_d_viewer.py` into testable TypeScript constants/helpers.
  - Splits wall segments around model openings so the native scene keeps the same door/window gaps as the current generated 3D viewer.

- `photoViewpoints.ts`
  - Defines camera presets matched to representative project photo directions, such as deck looking toward house, lounge looking SW/NE, sunroom looking NW/SW, kitchen looking NW, Bedroom 2 looking N/SW, laundry/entrance, and exterior front/sunroom approaches.

Add a Svelte component:

- `apps/desktop-ui/src/ThreeDNavigationView.svelte`
  - Loads data, builds the scene, manages renderer lifecycle, handles controls, shows toggles/presets/status, and cleans up Three.js resources on destroy.

### Rendering Layer

Use Vite imports:

```ts
import * as THREE from "three";
```

The existing frontend package already depends on `three@0.160.0`, so the native component should not use CDN import maps.

Use a full available workspace region as the 3D canvas. The scene should not sit in a decorative card. The primary interaction should be an immersive 3D view.

## Geometry Rules

Use metres as scene units.

Coordinate mapping should stay consistent with existing app data:

- furniture `x_m` maps to Three.js `X`
- furniture `y_m` maps to Three.js `Z`
- height maps to Three.js `Y`
- room and site display geometry comes from the same model transform already used by 2D/furniture logic

The 3D model should include:

- floors for all 11 current rooms
- exterior and interior walls with the curated opening cuts already used by the current 3D generator, ported into TypeScript rather than called through Python
- the sunroom polygon and wraparound glazing
- kitchen/dining deck doors and windows
- lounge openings and borrowed-light relationship to sunroom
- hallway/old front door relationship to sunroom
- entrance/laundry/toilet service area
- deck, deck steps, front diagonal path, driveway, garage/shed, cottage, lawn, hedge/fence context
- house floor raised 0.30m above ground on piles

Pile/foundation modelling:

- ground plane remains at `Y = 0`
- house floor platform starts around `Y = 0.30`
- deck height should sit close to the floor threshold where photos show continuity, but can be slightly lower if needed
- add visible pile/support posts under main exterior edges at practical intervals
- add a subdued foundation/skirt shadow plane so the house reads as raised without overcomplicating the subfloor

## Furniture Rules

The native 3D view must consume saved furniture layout objects, not only hard-coded fixture cues.

Each object should be converted from the saved `FurnitureObject` contract:

- `x_m`, `y_m`, `width_m`, `depth_m`, `rotation_deg`, `colour`, `layer`, `type`, and optional `l_shape`
- fixed and moveable furniture should both render
- z-index is not important for 3D vertical ordering, but can be used for deterministic build order
- furniture should sit on the raised floor height unless it is a site/deck object
- very thin fixed objects such as partition walls and wardrobe doors should preserve their intended thin width

Furniture shapes should be recognisable but pragmatic. Avoid over-modelled decorative meshes until basic placement/scale is correct.

Examples:

- L-shaped sofa: two rounded upholstered blocks, shared material, no overlap artefact, lower seat/arms/back forms
- L-shaped desk: two tabletop slabs and light legs/storage blocks, using saved `l_shape`
- piano: dark upright body, keyboard strip, top ledge
- bed: base, mattress, pillows/headboard
- dining table: tabletop, legs, chairs/stools if present
- kitchen cabinets: cabinet block, counter slab, sink/cooktop/fridge/pantry/appliance cues
- shower/bath/toilet/vanity: simple white wet-area fixtures with recognisable proportions
- fireplace/TV: wall-aligned elements, not floating cubes

## Materials And Photo Realism

Use photo-informed procedural materials first:

- kitchen cabinetry: dark blue/navy, semi-matte
- counters and wet fixtures: off-white/light neutral
- living/bedroom carpet: neutral beige/grey with subtle fibre noise
- kitchen/entrance/laundry flooring: warm vinyl plank
- bathroom: pale tile
- walls: warm off-white plaster, slight roughness
- trims/window frames: white
- glazing: transparent blue-grey with reflections and double-sided panels
- deck: warm timber with board lines
- concrete/paths: pale concrete with mild mottling
- lawn/hedges: green variation, not single flat green

The first native phase should avoid heavy external texture assets. Canvas-generated textures are acceptable and easier to test. Later passes can add local image textures if they materially improve realism.

## Lighting

Add a practical lighting system:

- hemisphere light for ambient sky/ground balance
- directional sun light with soft shadows
- warm interior fill lights in key rooms so navigation is usable
- exposure/tone mapping on the renderer
- shadow receiving on floors/site

Future link to sunlight:

- The scene config should reserve fields for season/time-of-day.
- Use the existing Christchurch/orientation assumptions from the reference-plan sunlight work when adding sun controls.
- In the first native pass, a few presets are enough: morning, midday, afternoon, winter-low, summer-high.

## UI Controls

The 3D view should include restrained controls overlaid on the scene:

- Reset view
- Photo viewpoint preset menu
- Toggle furniture
- Toggle fixed furniture
- Toggle moveable furniture
- Toggle roof/ceiling if added later
- Time/light preset if included in a later task
- Status text for loaded model/furniture source

Navigation should preserve current behaviour:

- drag/mouse look
- `W/S` forward/back
- `A/D` strafe
- `J/L` or arrow keys turn
- wheel or `Q/E` height
- reset view

## Testing And Verification

Test the data conversion separately from WebGL:

- `buildThreeDSceneConfig` includes all rooms and site elements
- scene config includes a 0.30m floor elevation/foundation setting
- scene config includes curated wall segments with door/window gaps
- scene config includes saved furniture objects from the layout
- L-shaped objects preserve leg dimensions
- partition walls and wardrobe doors remain thin
- material assignment uses model room/site/furniture types
- photo viewpoint presets exist and target expected room/site areas

Test the Svelte wiring by source inspection and component-level lifecycle where practical:

- `App.svelte` routes `three_d_navigation` to `ThreeDNavigationView`
- no iframe is used for the native 3D route
- `ThreeDNavigationView` imports Three and data command helpers
- controls/toggles are present

Visual verification is essential:

- launch the Tauri debug app
- open 3D Navigation
- inspect screenshot/pixels at desktop and smaller viewport sizes
- confirm the canvas is nonblank
- confirm furniture renders and scene is not clipped
- confirm navigation keys still work
- compare photo presets against representative photos

## Implementation Passes

This should be delivered in multiple passes rather than one risky rewrite:

1. Native app route and data loading, still simple geometry.
2. Scene config extraction from model and saved furniture.
3. Raised floor/piles/foundation/deck level.
4. Room floors, curated walls, openings, glazing, site context.
5. Furniture object rendering from saved layout.
6. Type-specific furniture forms.
7. Photo-informed materials and procedural textures.
8. Lighting, shadows, exposure, and interior fill.
9. Camera/photo presets.
10. Visual QA and cleanup pass.

After those, continue room-by-room realism passes:

- kitchen/dining
- lounge
- sunroom
- Bedroom 2
- master bedroom
- office
- hallway/bathroom
- entrance/laundry/toilet
- exterior/deck/front approach
- garden/site context

## Non-Goals

- No full Blender/GLTF asset pipeline in the first native phase.
- No AI-generated texture dependency for geometry correctness.
- No exact structural engineering claims about piles/foundation.
- No automatic inference of hidden dimensions from photos.
- No garden designer in this phase, though site context should prepare for it.
- No proposed scenario animation in the first pass, though the architecture should keep that path open.

## Risks

- The saved furniture layout may contain objects partly outside rooms or close to walls; the 3D renderer should render them faithfully rather than silently adjusting placement.
- Some photo-derived material choices are approximate and should not be treated as measured facts.
- Exact wall height/ceiling height is still approximate for some rooms.
- Sunroom geometry remains one of the least certain parts of the model.
- Too much visual detail too early could make navigation slow; keep the first pass performant.

## Success Criteria

The first native 3D realism milestone is successful when:

- 3D Navigation is rendered by a Svelte/Three component, not an iframe.
- It loads the latest saved furniture layout.
- The house reads as raised on piles about 0.30m high.
- The main room geometry, deck, sunroom, openings, and external context match the base view.
- Fixed and moveable furniture appear in their current saved positions.
- At least the major furniture types are recognisable.
- Materials and lighting are closer to the photos than the old generated viewer.
- The view is navigable with the existing keyboard/mouse controls.
- Full tests/build pass and the debug app is visually checked.
